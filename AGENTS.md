# ADR: Marketplace на микросервисах (React + Node.js)

Статус: Принято (v1.1) · Дата: 18 ноября 2026 · Тип проекта: pet-проект для изучения микросервисной архитектуры

## 0. Контекст и цели

Проект создаётся как учебный: главная цель — на практике понять, как компоненты микросервисного приложения взаимодействуют, ломаются и восстанавливаются. Поэтому там, где есть выбор между «проще» и «поучительнее», предпочтение отдаётся поучительному, но с контролем сложности.

**Цели**

- Понять асинхронное взаимодействие, согласованность данных и отказоустойчивость.
- Освоить контейнеризацию (Docker Compose).
- Сделать работающий маркетплейс: регистрация, каталог, корзина, оформление заказа, уведомления.

**Не цели (v1)**

- Платежи (в том числе mock-сервис Payments), доставка, поиск по полному тексту, отзывы, продавцы с кабинетами (можно добавить позже как отдельные сервисы).
- Высокая нагрузка, production-grade безопасность и миграция на Kubernetes.

**Принятые вводные решения (по опросу)**

| Вопрос | Решение |
| --- | --- |
| Коммуникация сервисов | Только асинхронно, через брокер |
| Брокер | RabbitMQ |
| Оркестрация | Docker Compose (Kubernetes вне scope) |
| Backend-фреймворк | Express (минимализм) |
| Базы данных | PostgreSQL + Redis |
| Состав сервисов | Стандарт: Auth, Catalog, Cart, Orders, Notifications |
| Frontend | React + TypeScript |

## ADR-001. Микросервисная архитектура и границы сервисов

**Решение.** Система состоит из пяти доменных сервисов, API Gateway и SPA-фронтенда. Каждый сервис владеет своими данными и деплоится независимо.

| Сервис | Ответственность | Хранилище |
| --- | --- | --- |
| **auth-service** | Регистрация, логин, выдача и обновление токенов, роли (buyer, seller, admin) | PostgreSQL |
| **catalog-service** | Товары, категории, остатки (stock) и их резервирование | PostgreSQL |
| **cart-service** | Корзина пользователя | Redis |
| **order-service** | Заказы, статусы, оркестрация процесса оформления | PostgreSQL |
| **notification-service** | Уведомления (email через mock/Mailhog, in-app) | PostgreSQL |
| **api-gateway** | Единая точка входа для фронтенда, проверка JWT, маршрутизация, rate limiting, SSE-поток событий для UI | Redis |

**Обоснование.** Границы выделены по бизнес-возможностям (bounded contexts), а не по техническим слоям. Пять сервисов — достаточно, чтобы появились настоящие межсервисные сценарии, и не слишком много для одного разработчика.

**Последствия.** Появляется дублирование части данных (например, снимок цены товара в заказе) — это осознанная цена независимости сервисов.

## ADR-002. Межсервисное взаимодействие: только асинхронно через RabbitMQ

**Решение.** Сервисы не вызывают друг друга по HTTP/gRPC. Всё общение — через события в RabbitMQ.

**Топология**

- Один **topic exchange** `marketplace.events`, ключи маршрутизации вида `<сервис>.<сущность>.<событие>`, например `catalog.product.updated`.
- У каждого потребителя своя durable-очередь (`<сервис>.<источник>`), привязанная к нужным ключам.
- Dead-letter exchange `marketplace.dlx` и очереди DLQ для сообщений, которые не удалось обработать после N повторных попыток (retry с задержкой).
- Сообщения в формате JSON с конвертом: `eventId`, `type`, `occurredAt`, `correlationId`, `version`, `payload`.

**Гарантии и правила**

- Доставка **at-least-once**, поэтому каждый потребитель обязан быть идемпотентным (таблица `processed_events` — Inbox pattern).
- Публикация события и запись в БД — атомарно через **Transactional Outbox**: событие пишется в таблицу `outbox` в той же транзакции, отдельный воркер публикует его в брокер.
- События версионируются (`version`); контракты лежат в общем пакете и валидируются через zod.

**Рассмотренные альтернативы**

- *Kafka* — мощнее (лог событий, replay), но тяжелее в эксплуатации. Для обучения на старте избыточна; можно подключить позже для аналитического потока.
- *Синхронные REST/gRPC* — отвергнуты по требованию проекта (цель — прочувствовать асинхронность).

**Последствия.** Eventual consistency везде; сложнее отладка (нужны correlationId и трассировка); нужно проектировать для повторов и дублей. Это и есть главный предмет изучения.

## ADR-003. Внешний API: API Gateway и read-модели

**Контекст.** Сервисы общаются между собой только событиями, но фронтенду нужны обычные запросы «дай данные» и «выполни команду».

**Решение.**

- Для **внешнего** трафика (браузер → система) используется HTTP/REST через api-gateway. Gateway проксирует запросы на HTTP-интерфейсы сервисов. Это граница системы, а не межсервисное общение; правило «никаких вызовов сервис → сервис» сохраняется.
- Данные, нужные сервису от других, он держит у себя в виде **локальной реплики (read-модели)**, обновляемой по событиям. Пример: order-service хранит копию `product_snapshot` (id, название, цена, продавец), наполняемую событиями `catalog.product.*`.
- Команды, запускающие длинный процесс (оформление заказа), возвращают **202 Accepted** с `orderId`; итог фронтенд получает через SSE: gateway подписывается на события order.order.\* собственной очередью и транслирует их в SSE-поток пользователя. Разовый GET статуса заказа нужен только при загрузке страницы и после переподключения потока.
- Gateway **не агрегирует** данные из нескольких сервисов синхронно (никакого API composition в v1).

**Последствия.** Данные в read-моделях могут отставать на доли секунды; UI должен корректно показывать промежуточные состояния («заказ обрабатывается»).

## ADR-004. Хранение данных: PostgreSQL и Redis

**Решение.**

- **Database per service**: у каждого сервиса, использующего PostgreSQL, своя логическая БД (в Compose — один инстанс Postgres с разными базами и пользователями). Прямой доступ к чужой БД запрещён.
- **Redis** используется для: корзины (cart-service), rate limiting и кэша в gateway, хранения blacklist/refresh-токенов (по необходимости).
- Доступ к Postgres — через **Prisma** (меньше шаблонного кода, строгая типизация); `schema.prisma` и миграции (Prisma Migrate) у каждого сервиса свои. Knex рассмотрен и отклонён.

**Обоснование.** Реляционная модель подходит для заказов и каталога; Redis естественен для эфемерных и быстрых данных вроде корзины.

**Последствия.** Нет межсервисных JOIN и распределённых транзакций — вместо них события, read-модели и саги (ADR-006).

## ADR-005. Backend: Node.js + Express + TypeScript

**Решение.**

- Node.js LTS, TypeScript в strict-режиме, Express 5.
- Единая структура сервиса: `src/api` (HTTP-слой), `src/domain` (бизнес-логика), `src/infra` (БД, брокер), `src/events` (публикация и обработка событий), `src/config`.
- Валидация входных данных и событий — **zod**. Логирование — **pino**. Конфигурация — переменные окружения с валидацией при старте.
- Брокер-клиент: **amqplib** с тонкой собственной обёрткой (подключение, переподключение, publish/consume, retry, DLQ). Писать её вручную — часть обучающей цели.
- Общие вещи (типы событий, схемы, обёртка брокера, logger) живут в пакете `packages/shared` внутри монорепозитория.

**Структура репозитория (monorepo, pnpm workspaces)**

```
marketplace/
  apps/
    web/                  # React + TS (Vite)
    api-gateway/
    auth-service/
    catalog-service/
    cart-service/
    order-service/
    notification-service/
  packages/
    contracts/            # схемы событий и DTO (zod)
    messaging/            # обёртка над RabbitMQ
    common/               # logger, errors, config
  deploy/
    compose/              # docker-compose.yml
  docs/adr/
```

**Последствия.** Express не навязывает структуру, поэтому дисциплину нужно держать самому; это плата за понимание «как всё устроено».

## ADR-006. Согласованность: Saga для оформления заказа

**Решение.** Оформление заказа — **хореографическая сага** на событиях, без центрального оркестратора.

**Основной сценарий**

1. Фронтенд → gateway → order-service: `POST /orders` (из содержимого корзины).
2. order-service создаёт заказ в статусе `PENDING` и публикует `order.order.created`.
3. catalog-service пытается зарезервировать остатки → публикует `catalog.stock.reserved` или `catalog.stock.rejected`.
4. order-service при `reserved` переводит заказ в `CONFIRMED` (публикует `order.order.confirmed`), при `rejected` — в `CANCELLED` (`order.order.cancelled`).
5. cart-service очищает корзину по `order.order.confirmed`.
6. notification-service отправляет уведомление по `confirmed` / `cancelled`.
7. При отмене подтверждённого заказа catalog-service освобождает резерв по `order.order.cancelled` (компенсирующее действие).

**Платёж** в v1 не моделируется, отдельный сервис Payments не создаётся. Если понадобится, платёж добавляется как шаг саги (mock payment) без изменения остальной архитектуры.

**Последствия.** Нужно учитывать таймауты (заказ завис в `PENDING` → автоматическая отмена по таймеру) и защиту от гонок/дублей.

## ADR-007. Карта событий

| Событие | Источник | Потребители | Назначение |
| --- | --- | --- | --- |
| `auth.user.registered` | auth | notification | Приветственное уведомление |
| `catalog.product.created` / `updated` / `deleted` | catalog | order, cart | Обновление локальных реплик товара |
| `order.order.created` | order | catalog | Запуск резервирования остатков |
| `catalog.stock.reserved` / `rejected` | catalog | order | Результат резервирования |
| `order.order.confirmed` | order | cart, notification, gateway (SSE) | Очистка корзины, уведомление |
| `order.order.cancelled` | order | catalog, notification, gateway (SSE) | Освобождение резерва, уведомление |

Схемы событий версионируются и хранятся в `packages/contracts`.

## ADR-008. Аутентификация и авторизация

**Решение.**

- **auth-service** выдаёт пару токенов: короткоживущий JWT access-токен (≈15 минут), подписанный асимметричным ключом (RS256/EdDSA), и refresh-токен (хранится хэшированным; ротация при использовании).
- **api-gateway** проверяет подпись access-токена публичным ключом (локально, без обращения к auth-service) и передаёт сервисам `x-user-id` и `x-user-roles`.
- Сервисы доверяют заголовкам только из внутренней сети (в Compose — внутренняя сеть без публикации портов).
- Авторизация на уровне ролей (buyer, seller, admin) — на уровне эндпоинтов сервисов.

**Последствия.** Мгновенный отзыв access-токена невозможен (только по истечению срока); для pet-проекта это приемлемо и само по себе полезный компромисс для изучения.

## ADR-009. Frontend: React + TypeScript

**Решение.**

- Vite, React 18+, TypeScript strict.
- Роутинг — React Router; серверное состояние — **TanStack Query** (кэш; данные обновляются по SSE-событиям, при обрыве потока — повторный запрос статуса); клиентское — Zustand или контекст.
- Формы — React Hook Form + zod (переиспользуем схемы из `packages/contracts`, где уместно).
- UI-библиотека: Tailwind CSS + компоненты shadcn/ui (или MUI — по предпочтению).
- Фронтенд общается только с api-gateway.

**Основные экраны:** каталог и карточка товара, корзина, оформление заказа, мои заказы, логин/регистрация, простая админка (CRUD товаров) для роли seller/admin.

## ADR-010. Запуск: Docker Compose

**Решение.**

- **Docker Compose:** все сервисы, Postgres, Redis, RabbitMQ (с management UI), Mailhog и фронтенд поднимаются одной командой `docker compose up`. Для каждого сервиса — многостадийный Dockerfile, healthcheck, `depends_on` с условием healthy.
- Правила для всех сервисов (12-factor): конфигурация только через env-переменные, graceful shutdown по SIGTERM, stateless-сервисы, логи в stdout.

**Последствия.** Нет автомасштабирования, rolling update и самовосстановления кластера; для v1 достаточно restart-политик Compose. Kubernetes исключён из текущей версии.

## ADR-011. Наблюдаемость и тестирование

**Наблюдаемость**

- Структурные JSON-логи (pino) с `correlationId`, который сквозно передаётся в заголовках HTTP и в конверте события.
- Эндпоинты `/health/live` и `/health/ready` в каждом сервисе.
- Позже: метрики (Prometheus + Grafana) и трассировка (OpenTelemetry + Jaeger), включая трассировку через RabbitMQ.

**Тестирование**

- Unit-тесты доменной логики: Vitest.
- Интеграционные тесты сервисов с реальными Postgres/Redis/RabbitMQ через **Testcontainers**.
- Контрактные проверки схем событий (zod-схемы в `packages/contracts` как единый источник правды).
- E2E-сценарий «регистрация → корзина → заказ → уведомление» (Playwright или скрипт).
- Хаос-эксперименты для обучения: остановить сервис, продублировать сообщение, переупорядочить события.

**CI:** GitHub Actions — lint, typecheck, tests, сборка образов.

## Последствия и риски (общие)

| Риск | Митигация |
| --- | --- |
| Чрезмерная сложность для одного разработчика | Строго держать scope v1 (5 сервисов), реализовывать по вертикальным срезам |
| Потеря или дублирование сообщений | Outbox + Inbox, идемпотентность, DLQ |
| Сложная отладка асинхронных потоков | correlationId, структурные логи, RabbitMQ UI, позже трассировка |
| Дрейф контрактов событий | Единый пакет `contracts`, версионирование, контрактные тесты |
| Затягивание из-за инфраструктуры | Только Docker Compose; Kubernetes вне scope |

## План этапов

Разработка идёт вертикальными срезами: каждый этап заканчивается работающим сценарием в Docker Compose.

| № | Этап | ADR | Что делаем | Критерий готовности |
| --- | --- | --- | --- | --- |
| 1 | Фундамент | 005, 010, 011 | pnpm-монорепозиторий, пакеты `contracts`, `messaging`, `common`; Compose с Postgres, Redis, RabbitMQ, Mailhog; обёртка над amqplib; Prisma в каждом сервисе; CI | `docker compose up` поднимает инфраструктуру, тестовое событие проходит путь publish → consume |
| 2 | Auth + Gateway | 008, 003 | Регистрация, логин, JWT и refresh-токены, проверка подписи в gateway, каркас React-приложения | Пользователь входит через фронтенд, запрос без токена отклоняется gateway |
| 3 | Catalog | 001, 004, 007 | CRUD товаров, события `catalog.product.*`, страницы каталога и карточки товара, простая админка для seller | Товар, созданный в админке, виден в каталоге |
| 4 | Cart | 004, 007 | Корзина на Redis, локальная реплика товаров по событиям | Корзина сохраняется между сессиями, смена цены товара доходит до cart-service |
| 5 | Orders + saga | 006, 007 | `POST /orders` → 202 и `PENDING`, резервирование остатков, `CONFIRMED` / `CANCELLED`, очистка корзины | Заказ доходит до `CONFIRMED`; при нехватке остатков получает `CANCELLED` |
| 6 | SSE и статусы в UI | 003, 009 | Gateway подписан на `order.order.*` и ведёт SSE-поток, авторизация потока через fetch-стрим с JWT, heartbeat, разовый GET статуса после переподключения, обновление TanStack Query | Статус заказа меняется на экране без перезагрузки страницы |
| 7 | Notifications | 007 | Подписки на события, Mailhog, in-app уведомления | После `confirmed` / `cancelled` письмо приходит в Mailhog; E2E «регистрация → корзина → заказ → уведомление» проходит |
| 8 | Надёжность | 002, 006 | Outbox и Inbox, retry и DLQ, таймаут заказа в `PENDING`, хаос-эксперименты | Дубль сообщения не создаёт повторного эффекта, остановка сервиса не теряет события |
| 9 | Наблюдаемость | 011 | Prometheus и Grafana, OpenTelemetry и Jaeger | Заказ прослеживается сквозной трассировкой через RabbitMQ |

## Закрытые вопросы

- **Доступ к БД:** Prisma (Knex отклонён).
- **Обновление UI после асинхронного действия:** SSE, без polling.
- **Сервис Payments:** не нужен в текущей итерации; к вопросу вернёмся после v1.
- **Kubernetes:** исключён из scope; вопрос Kustomize или Helm снят.
